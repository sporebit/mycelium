## Auth & middleware

**As built since P12 (2026-09-15): see `claude/spec-access.md`** — Supabase Auth identity, spaces + entity registry, `app.accessible_spaces()` policies, `createUserClient()` / `withUser()`, the gate order (public paths → PC metrics → CRON/API secrets → `mtk_` tokens → session → break-glass → sensitive paths), teams/grants/invites, audit, rate limits, export/delete, rundowns. **2026-10-29:** `/api/health` is public *exactly*; as a prefix it had let every `/api/health/*` route skip the gate (`41c5035`). The paragraph below is the **pre-P12** description, kept for history.

*(Historical, pre-2026-09-15)* `middleware.ts` gates everything except `PUBLIC_PREFIXES` (`/login`, `/api/auth/*`, `/api/telegram/webhook`, `/api/cron/reminders`, `/api/health-import`, `/api/cron/drops-monitor`). Four ways in: HMAC-signed `auth-token` cookie (secret `AUTH_SECRET`, 30-day, verified in middleware via WebCrypto; `lib/auth/cookie.ts`); `x-api-secret` header (`API_SECRET`, CLI/programmatic); `Authorization: Bearer CRON_SECRET` (scheduled functions); and path-scoped `Bearer PC_METRICS_SECRET` for `/api/studio/pc-metrics` only (agent POST + future headless Pi GET — added when the previously public GET was closed). API routes 401; pages redirect to `/login`. Server data access via `createServerClient()` (`lib/supabase/server.ts`, service role, bypasses RLS) — the single most connected function in the codebase (238 edges). A browser client (`lib/supabase/client.ts`, anon key) exists. No Supabase Auth, no `@supabase/ssr` today; the single user is identified by the `USER_ID` env value stored as `user_id text` on 45 tables. `push_subscriptions.user_id` is the one `uuid references auth.users(id)` column. Multi-user replaces all of this — see `claude/multi-user-plan.md` (Phase 2 identity, Phase 4 authorisation).

**RLS coverage (from migration files, 2026-09-06):** tables from 0001–0046, 0059 and 0092–0096 have RLS + deny-all + service_role grant; `reminders` (0044) uses a `current_setting('app.user_id')` policy instead; ~30 tables created 0051–0090 (blood tests, agents, accounts, gut health, eye prescriptions, recipes/shopping/meal plan, media episodes, events, investments, spotify tokens/plays, ventures, drops, weather cache, bins) have no RLS. With Supabase's default grants that makes them reachable via the anon key. Fix = Multi-user Phase 0.

## Capture pipeline

**As of 2026-11-20 (master run Stream A; migrations 0159, 0162, 0163; MYC-183). This paragraph overrules anything below it that disagrees.** A capture is **received, then processed**: `lib/capture/pipeline.ts` `receiveCapture()` is one insert into `raw_captures` (`status = received`, a placeholder classification, idempotent on `client_uuid`, which is unique per space) and the route answers **202 `{ ok, status: "saved", capture_id }`** at once; `processCapture()` runs after the response (`after()`): weight shortcut, split, classify, file. If it fails the row is `failed` with its error and `lib/capture/sweep.ts` (each capture request, and the nightly cron for every user) finishes it, up to three attempts. **Every reply carries `ok` and a `status` word** because an iPhone Shortcut cannot read an HTTP status. Doors: `/api/capture` (words; the Shortcut's two-step send with `await_edit` then `final`/`edited`), `/api/capture-audio` (multipart, or since 2026-11-21 the recording as the whole request body: any Content-Type that is not multipart/form-data is read as the file, named `<client_uuid>.m4a`, typed by that header with audio/m4a for none or application/octet-stream, `client_uuid`/`text`/`kind` from the query string; same answer, dedupe and host size cap; needed because the iPhone Shortcuts are now compiled with Cherri, which can only send a file as the body; the recording is kept in the `captures` bucket under the capture's id and a `transcribe` job is queued for the PC; cloud transcription only when the PC has not checked in and the cap allows), `/api/capture-photo` (kept with the capture; no model reads it). **Review queue = every capture not yet reviewed, discarded or auto-filed** (`lib/capture/queue.ts` `waitingForReview`); a card left **seven days** files itself tagged `unreviewed` (`lib/capture/autofile.ts`, nightly). A long capture is **split** (`lib/capture/split.ts`): each item is a child row held as an idea with a suggested kind, the parent is reviewed at once, and each child plays the parent's recording. **A hand edit wins** over any transcript (`text_edited`, `lib/capture/transcript.ts` `chooseText`). A capture's card is answered when its ticket leaves the Inbox by any route (trigger `tickets_settle_capture_card`, 0163); accepting the card moves the ticket on. Reminders are set from spoken times (`lib/capture/reminderDue.ts`). Feedback: "Saved" in the reply, then a push "Filed as …" linking the card (`lib/nudges/interrupt.ts`, origin `reply`, outside the interruption budget). **Job queue** (0159): `jobs` + `claim_jobs`/`finish_job` with leases and back-off, `workers` heartbeat, `/api/worker/claim` and `/finish` (Bearer `CRON_SECRET`), results applied as the job's owner; `pc-worker/worker.mjs` on the PC (Whisper `large-v3-turbo`, Ollama). **Phone credentials:** an API token with the `capture` and `daily` route families (`lib/system/apiTokens.ts`); tokens work end to end only since 2026-11-20. The iPhone Shortcuts are a written build guide: `docs/checklists/iphone-shortcuts.json`. Not built: recordings over about 4 MB (one request is capped by the host), classification on the PC's model, removing a deleted capture's recording.

Inbound: Telegram bot webhook `/api/telegram/webhook` and iOS Shortcuts → `/api/capture-audio` (voice) / `/api/capture`. Whisper transcription (OpenAI), then classification → routing rules (`routing_rules`, 0021, editable at `/the-boys/rules`) → entity creation with review queue (`/organisation/captures/review`; UI-created entities bypass review, automated ones route through it; `entity_review_rules` 0034). Pending-entity and pending-route resolution endpoints; `capture_source_labels` config (0086). Voice failures must reply in Telegram and preserve `file_id` — never silently drop. Outbound Telegram via `/api/telegram/send` (also shopping-list send).

**As of 2026-10-29.** One classifier, `lib/router/classifyCapture.ts` `classifyCapture()`, serves all three inbound routes (Telegram, `/api/capture`, `/api/capture-audio`). Its prompt = the user's routing rules + `CLASSIFIER_SYSTEM_PROMPT` + a **few-shot block built from `capture_learning`** (`lib/capture/learning.ts` `buildFewShotBlock`, cached per user, invalidated on approval) + the ignored-kinds block. **Kinds** the classifier can return: `task`, `note`, `decision`, `idea`, `journal`, `workout`, `purchase`, `pain_log`, `reminder`, `media`, `account`, `quote`; the registry test fails if any of them lacks a registry entry. A `task` becomes a ticket in Inbox (`kind === "ticket"` is the typed form of the same thing); `person` exists only as a typed kind, never a classifier intent (the capture rule: tickets link existing people only).

**Typed capture (MYC-161, 0138).** `lib/capture/registry.ts` is the one field registry: `TYPED_KINDS` = task, ticket, reminder, purchase, media, quote, journal, idea, decision, note, person, account, pain_log, workout; each `EntityDef` lists its fields (type, options, person pickers, hidden fields such as `waiting_on_person_id`), `classificationForTyped()` turns a filled form into the same classification shape the LLM would have produced, and `toPostBody` whitelists what reaches the API. The web capture form posts a typed kind straight to the review queue; **the classifier still runs in the shadow** (`usageTag: capture.shadow`, metered in `api_usage`) so the prediction can be compared with what the user chose. `capture_learning` (one row per `raw_captures` row): `predicted_kind/fields/llm_source` at capture, `chosen_kind/fields` from the form, `approved_kind/fields/at` on review approval (`recordPrediction` / `recordApproval` / `recordTicketApproval`, the last from the ticket move route). The approved rows are what the few-shot block is built from, so corrections teach the classifier without a model change.

**Review** (`/organisation/captures/review`, `app/api/captures/[id]/review/route.ts`): APPROVE materialises by kind — person, task/ticket, journal, purchase, media, reminder, pain_log, account, quote (MYC-151…156) — re-keying a changed kind and re-routing a quote to Quotes; `lib/captures/reviewCount.ts` feeds the pending badge.

## Agents — The Boys (`/the-boys`)

Chat + voice (silence-detection loop, TTS via `/api/agents/tts`) with tool-calling and confirm-before-execute cards (`[agentId]/confirm-tool`). 7 agents incl. "Da Boi" (cross-domain, keyword-heuristic context diet from P11), The Founder (ventures tools: create_venture, add_venture_step), a nutritionist (0066), founder/engineer agents (0073). System prompts are built in one place, `lib/agents/system.ts` `buildAgentSystemPrompt()` (persona from `lib/agents/prompts.ts`, memory summary, Da Boi's keyword-scoped domain diet with live one-liners, the day-log diet for Da Boi and the persona agent, the user's **manner** instruction (MYC-149), the spoken suffix for voice turns (MYC-148), tool suffix) with cache_control breakpoints (P11; note: an agent under ~1024 prefix tokens won't cache — `fitness` doesn't). **2026-10-29:** the fitness and nutrition agents get a **live context** block on every fresh turn (`lib/agents/live-context.ts`: programme + week of phase, today's plan, last 7 days, pain; targets with review date, today's intake, 7-day average, gut, recipe library) — read-only, never written to memory. Voice per agent (`agent_voices`, 0136) and streamed voice turns via `lib/agents/anthropicStream.ts`. Model ids centralised in `lib/config/models.ts`; Haiku for classification/extraction, Sonnet for vision scans. ## Integrations

- **Google Calendar**: OAuth (`/api/google/auth|callback`), tokens as columns on `user_settings` (0088), event ids 0089, sync via `/api/google/sync` + `/api/cron/google-sync`. **Since 0184 (2026-11-22, `claude/family-calendar-spec.md` §4.5) the sign-in is locked:** `/api/google/auth` sets a `state` cookie that the callback must match before the code is spent; the account that consented is read from Google and must be in `GOOGLE_ALLOWED_ACCOUNTS` (empty = nobody), otherwise the token is revoked on the spot and nothing is stored; the connected address is kept in `user_settings.google_account_email` and shown in Settings → Integrations, which also says in words why a sign-in was refused (`?google=not_allowed|bad_state|no_account`). **2026-11-23, reconnect came back as `bad_state` every time:** CONNECT / RECONNECT were Next `<Link>`s, and the app router prefetches a link's href as soon as it is on screen and on hover, so `/api/google/auth` ran several times per visit to Integrations and each run replaced the nonce cookie; a click went through the router too (an RSC fetch that follows the redirect to Google, then a full navigation), so the nonce in the link and the nonce in the cookie no longer agreed. Fixed three ways (`lib/google/oauth.ts`): the links are plain anchors; the auth route answers any router-made request (`Next-Router-Prefetch`, `RSC`, `Purpose: prefetch`) with 204 and no cookie; and the cookie keeps the last five nonces (`packStates` / `stateAccepted`), so a second click or tab does not break a sign-in under way. The cookie is set and cleared with the same attributes (Path `/api/google` — it must reach the auth route too, or a second start cannot see the nonces already waiting; Secure on https, HttpOnly, Lax, 10 min; the callback also clears the pre-2026-11-23 cookie at `/api/google/callback`); the redirect URI is built from the request origin (`mycelium.sporebit.com`, no `www`), there is no `GOOGLE_REDIRECT_URI` variable. The callback now returns to `/other/settings?tab=integrations&google=<flag>`, and Settings treats `?google=` with no `tab` as Integrations, so the notice is seen (`connected` reads "Reconnected as <address>"; a connection without a stored address reads "account unknown, reconnect to confirm"). Tests: `app/api/google/roundtrip.test.ts` (auth → callback with the cookie, the attributes, two starts, router fetches get 204, refusals), `e2e/google-connect.tess.spec.ts` (no prefetch of the links, a real click round trip with Google stubbed, two tabs, the flag opening Integrations). `GOOGLE_ALLOWED_ACCOUNTS` was still unset on Vercel on 2026-11-23: until it is set every account is refused with `not_allowed`. `lib/google/calendar.ts` gained status-aware calls (`calRequest`, calendars, ACL, events with sync tokens, watch/stop channels) beside the older null-on-failure ones. The **Family calendar** sync itself is in `lib/family/calendar/{map,sync}.ts` (organisation spec, Family → Calendar tab).
- **Spotify**: OAuth, tokens in `spotify_tokens` (0069, single row, no RLS — see above), plays 0070; now-playing, recently-played, top artists/tracks, sync-plays; dashboard at `/studio/spotify`.
- **Apple Health**: Health Auto Export iOS app → POST `/api/health-import` (`HEALTH_IMPORT_SECRET`), one row per metric per day (0045). Code done; activation still pending (secret + app config — on the backlog).
- **Telegram**: capture + reminders + drops alerts + shopping lists. `user_settings.telegram_chat_id` exists per user (0075) but only Phil's chat is wired.
- **Push**: web-push, subscriptions 0039, `/api/push/send|subscribe`.
- **Weather/sun**: `/api/weather` (3h server cache, 0087) + `/api/sun`; chips in Today TimelineRail.
- **Bins**: `bin_schedule` 0090, `/api/bins/next|sync` — Doncaster council bin collection days, surfaced on the Today timeline.
- **Email**: Resend via `lib/system/email.ts` (invites, Work notifications, rundowns); without `RESEND_API_KEY` the invite link is shown to the inviter instead.

**Inbound webhooks (2026-10-29 list).** All are public prefixes and verify their own secret in the handler: `/api/telegram/webhook` (`x-telegram-bot-api-secret-token` = `TELEGRAM_WEBHOOK_SECRET`), `/api/tickets/github` (HMAC-SHA256; a commit or PR that names a key moves the ticket to Verify on merge to `main` — a *test* ticket key in a commit auto-closes it, `tickets-spec` §7.1), `/api/tickets/vercel` (HMAC-SHA1 `x-vercel-signature` with `VERCEL_WEBHOOK_SECRET`; `deployment.succeeded` on production runs the smoke for every In Review ticket carrying code evidence and moves it to Done), `/api/health-import` (`HEALTH_IMPORT_SECRET`, Apple Health). Each acts as a user through `withUser()` chosen by `lib/system/bindings.ts`. **Added 2026-11-22:** `/api/google/push` (POST only; Google's calendar push channel: the `x-goog-channel-id` and `x-goog-channel-token` headers must match the stored channel, looked up through `lib/system/familyCalendarChannel.ts`; the only effect is a pull as the connection's owner; anything else is answered 200 and ignored). ## Cron

**As of 2026-11-20 (MYC-187).** One route, **`/api/cron/tick`** (Bearer `CRON_SECRET`, GET or POST, `?dry=1` lists what is due), runs everything that must happen during the day. The schedule is a table in `lib/system/schedule.ts` (five-minute slots, London time): daily prompts every 5 min 06:00–24:00, reminders every 5, check-ins every 15, Day log every 15 from 18:00 to 04:00, quote research every 30, rundowns hourly; **from 2026-11-22** `/api/cron/family-calendar` every 15 (pull the Family calendar from Google, renew the push channel under two days before it lapses, and once a day the connection health check: a failure is written down, pushed to the owner once a day with the reconnect link and raised as one dated ticket) and `/api/cron/jobs` every 5 (**the cloud lane of the job queue**, `lib/jobs/cloud.ts`: claims jobs whose handler has `run`, runs them as the job's owner, finishes or backs off; before this nothing drained lane `cloud`). Every job is safe to run twice. **The PC worker knocks every five minutes while the PC is on**; one cron-job.org job (MYC-180) covers the PC being off. The per-route cron-job.org jobs described below still work and may stay.

Vercel Hobby caps cron at daily (100 jobs, once per day, fires within the hour) and since 2026-11-19 **rejects the deploy** if `vercel.json` holds a sub-daily expression. **cron-job.org** therefore drives every sub-daily job (`docs/cron-migration.md`): `/api/cron/reminders` (Bearer `REMINDERS_CRON_SECRET`, a distinct env var), `/api/cron/drops-monitor`, `/api/cron/google-sync`, and from 2026-11-19 `/api/cron/rundowns`, `/api/cron/tickets-checkins`, `/api/cron/quotes-research`, `/api/cron/daylog` (all Bearer `CRON_SECRET`, GET, UTC). **`vercel.json` as of 2026-11-19** (all under `CRON_SECRET`, principal `system`, each route picking its user with `withUser()`):

## Notifications (Work, 0145 — 2026-09-30)

`notifications` (one row per recipient per event: `mention`, `assignment`, `status_change`, `comment`; `delivered` jsonb stamps per channel; a restrictive policy so only the recipient reads or changes a row). Written by the actor (`lib/work/notify.ts` `recordEvents` → watchers + assignee + mentioned), then **delivered as the recipient** in `after()` by `lib/system/notifyDeliver.ts` under `withUser(recipient)` so their prefs, push subscriptions and the stamp are all under their own RLS; the service client is used only for the recipient's email address. **Channels** (`lib/work/notifyPrefs.ts`): `in_app`, `telegram` (owner only — one chat wired), `email` (Resend), `push` (web-push, 0039); a per-event × per-channel grid in `user_settings.notification_prefs` plus quiet hours (London, Telegram/email/push suppressed, in-app always). A failing channel is logged and never fails the request. Surface: `/work/notifications` (read, delete). Rundowns use the same four channels (`claude/spec-access.md`).
