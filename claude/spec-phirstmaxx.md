# PhirstMaxx — as built (phase 1)

*Written 2026-11-22 by the Claude Code session that built phase 1 of `claude/phirstmaxx-spec.md`. The repo is ground truth; where this doc and the code disagree, fix the doc. The brief's decisions D1–D5 and the "never fail us" rules (§2 there) stand; this doc records what landed, where, and what did not.*

## 0. Shape

PhirstMaxx is a section (`phirstmaxx`) that lives in the **family team's space**: whoever is in the family team (the team whose space holds a `family_profile` row, lane DC / 0171) reads and writes it, nobody else sees a row. `pmCtx()` in `lib/phirstmaxx/server.ts` resolves the space through `familyCtx()` and seeds it the first time anyone opens the section (`pm_seed_space`: the starter block types and one `pm_people` row per team member).

Code: `lib/phirstmaxx/` (pure `engine/`, `research/` with injected-fetch `readers/`, one `adapter.ts` that touches other sections' tables), routes `app/api/phirstmaxx/*`, pages `app/phirstmaxx/*`, components `components/phirstmaxx/*`. Nav: `lib/nav/sections.ts` (Home, Week, Things, Plans, Settings), Life → PhirstMaxx in the new shell's menu, five card blurbs in `lib/nav/cards.ts`, a dormant-feature entry keyed `phirstmaxx` (weekly cadence over `pm_blocks`, `pm_drops`, `pm_plan_responses`).

## 1. Migration 0185

The section is admitted by **four** check constraints, not the two the brief named: `team_member_sections` and `user_grants_section_shape` (0110), `entity_groups_section_check` (0103, the list `register_table` files into) and `rundown_settings_sections_shape` (0115, which sections a team rundown may cover; the settings card sends every section it knows, so the multiuser lifecycle spec caught this one). The self-check at the end of 0185 fails if any of the four lacks `phirstmaxx`.

| Group | Tables |
|---|---|
| `phirstmaxx.time` | `pm_people` (one per member: name, colour, has_car, `waking` and `buffers` jsonb, `home_place_id`, `settings` jsonb, hashed inbox token + last-four hint), `pm_places`, `pm_block_types`, `pm_blocks` (half-hour check, firmness, `series_id`, `local`, `undo_batch`, `entered_by`), `pm_waking` (per-day overrides), `pm_patterns`, `pm_undo`, `pm_pets` |
| `phirstmaxx.things` | `pm_things`, `pm_drops` (`client_id` unique per space; must carry a link, words or a picture), `pm_thing_facts` (unique on thing, key, source kind and source URL), `pm_research_runs` (unique on drop and stage), `pm_travel` (unique on thing, origin place, mode), `pm_api_calls` (one row per space, provider, product and month) |
| `phirstmaxx.plans` | `pm_plans`, `pm_plan_responses` (one per plan per person), `pm_plan_legs`, `pm_notifications` |

Every table goes through `app.register_table` (space_id and created_by adopted, RLS on, the four `accessible_spaces` policies, service_role grant). `pm_thing_facts`, `pm_research_runs`, `pm_travel`, `pm_plan_responses` and `pm_plan_legs` are registered as children of their parent row. Every table that the importer fills has an `old_id text` with a unique index per space, which is what makes the import idempotent.

Functions: **`pm_save_blocks(space, person, ranges jsonb, type, firmness, place, title, repeat_until date, policy)`** saves one painted week in one transaction (`replace` cuts existing blocks where new ones land, `trim` cuts the new ranges around existing blocks; weekly repeats are laid in London wall-clock up to `repeat_until`; adjacent same-shape blocks merge; the originals go into `pm_undo` as one batch) and returns `{batch_id, created, removed, trimmed, series_id, weeks}`; **`pm_undo_blocks(space, batch)`** puts a batch back within ten minutes; **`pm_seed_space(space)`** (security definer, called by `pmCtx`); **`pm_count_api_call(space, provider, product, cap)`** counts a Google call against the month and returns false past the cap, so the bill cannot leave £0 (spec §11.2). A private storage bucket `phirstmaxx` (path `<space id>/…`, read and write by `phirstmaxx.things` view / create_delete) holds dropped pictures.

Registry: `lib/access/registry.ts` lists the section and the three groups; the registry coverage test proves every `pm_*` table is classified against the live local database.

## 2. The engine (`lib/phirstmaxx/engine/`, pure)

Re-expressed from the old app's engine with its decisions log (`A:\Projects\PhirstMaxxing\CLAUDE.md`) as the requirements list and its test fixtures as the acceptance suite. Modules: `time` (London wall-clock, half-hour slots), `intervals`, `recurrence` (a hand-written RRULE subset: FREQ, INTERVAL, BYDAY, UNTIL, COUNT), `expand` (series → concrete blocks), `windows` (`findWindows`: both awake, both free, buffers by block kind, per-day overrides, cross-midnight), `travel` (`distanceKm`, `travelMinutes(km, mode)` as the estimate of last resort), `score`, `chains`, `preferences`, `trip`, `sky` (sun and moon maths for best-time-of-day), `fit` (`fitThing(FitInput) → FitResult[]`, `nextFit(results, now)` → "fits this Saturday"). 152 vitest checks; `engine/PORT-NOTES.md` records every deliberate difference from the old engine. No database or network inside.

## 3. The weekly grid

`components/phirstmaxx/WeekGrid.tsx` + `SaveBar.tsx` + `lib/phirstmaxx/grid.ts` (21 checks): always 7 days × 48 half-hour rows, Monday first, opened at the person's waking start; click-and-drag multi-select of several ranges (Excel-style, additive), together-windows shaded across the day pair, an overlap preview before saving, one save of every selected range together through `pm_save_blocks` (`replace` or `trim`), Undo for ten minutes. Either person may paint the other's shifts; the block records who entered it.

## 4. Drops and research

A drop is stored first and researched later (spec §2 rule 1): `createDrop()` is one insert and one job enqueue (`pm_research`, lane cloud, dedupe on the drop) and answers 202 in well under a second; the same `client_id` twice returns the first drop with `duplicate: true`. Readers (`lib/phirstmaxx/research/readers/`, injected `fetch`, 62 checks): `website` (JSON-LD, Open Graph, opening hours), `youtube` (Data API when keyed, oEmbed otherwise), `social` (Instagram, Facebook, TikTok: oEmbed and caption only; no scraping), `exif` (GPS and date out of a photo), `geocode` (`nominatimSearch`, `googlePlacesFind` when keyed), `osm` (`overpassAround`, `osmFacts`), `routing` (`routeWithFallback`: Google Routes → OpenRouteService → the engine estimate, every answer tagged with its provider), `hours` (`OpeningHours` from schema.org, OSM or Google; `isOpenFor`).

## 5. The research pipeline (`lib/phirstmaxx/research/pipeline.ts`)

The `pm_research` job handler, registered from `lib/jobs/register.ts` and run by the cloud lane (`/api/cron/jobs`, every five minutes) as the drop's owner. One `pm_research_runs` row per stage: **read → resolve → enrich → travel → fit → notify**. Each stage runs in its own try/catch; a failure records `failed`, the attempt count, the error and `run_after = now + min(60, 2^attempts)` minutes, and never stops a stage that does not depend on it (travel, fit and notify depend on resolve; enrich does not block travel). When any stage is still failed and retryable the job throws so the queue brings it back; when every stage is done or skipped the job finishes. `force` re-runs done stages.

- **read**: website → `readWebsite`; YouTube → `readYouTube`; Instagram, Facebook, TikTok → `readSocial` plus the shared words; a picture → `parseExif` on the stored bytes then **vision** (`research/vision.ts`: one Messages API call with the image, asking for place name, town, signage, scene and a confidence). The result waits in `pm_research_runs.detail` until resolve gives it a thing.
- **resolve**: `nominatimSearch`, then `googlePlacesFind` when `GOOGLE_MAPS_API_KEY` is set and `pm_count_api_call(space, 'google', 'places', 900)` allows; an existing thing within 150 m (`nearDuplicate`) takes the drop, else a new thing is made (status researching). **No name at all** → `pm_drops.question = "What's this place called?"`, thing status `needs_answer`, stage `waiting`, the dropper told once; `answerQuestion()` (POST `/api/phirstmaxx/questions`) stores the answer as a person fact and re-queues with force.
- **enrich**: official-site facts → `overpassAround` + `osmFacts` → Google Place Details (counted) → the **web-search model call** (`research/websearch.ts`, the quotes pattern, `max_uses 3`; every fact must carry a cited URL, uncited claims are dropped). Facts are upserted (select then insert/update per thing, because the unique index uses `coalesce(source_url, '')`, which PostgREST's `onConflict` cannot name) and never overwrite a fact a person edited. The best fact per key is folded into the thing's columns except keys in `hand_edited`; `last_researched_at` set, `next_recheck_at` ninety days on, status `ready`. Opening hours live as the fact `opening_hours` in the engine's shape.
- **travel**: every saved place of every person × drive, walk, cycle (+ transit when Google is keyed) through `routeWithFallback` (Google counted against 900 a month, OpenRouteService when `ORS_API_KEY`, else the engine estimate) into `pm_travel` with its provider.
- **fit**: `fitsForThing` → the next fit's words as the fact `next_fit` (source kind estimate).
- **notify**: one push to the dropper, "<name> — 55 min each way, about 3 h there, fits this Saturday", with the thing's link; counts against the day's interruption budget.

**The paid rule (spec §11.5).** A model call (vision or web search) runs only when the instance owner's `pm_people.settings.research_cap_pence` is set: `0` means the shared £5 cap (`cloudAllowed`), a positive figure is PhirstMaxx's own monthly cap compared with this month's `pm_research_runs.cost_pence`, and unset means **not yet allowed** — the stage is `skipped` with the error "Research spend not yet allowed (checklist 7.1)" and the status line says so (`researchStatus().paid_allowed = false`). Every call's cost goes into `pm_research_runs.cost_pence` and `api_usage` under `phirstmaxx.research`. Status: `researchStatus(db, spaceId)` → queue depth, stuck runs, last success per source, this month's pence, whether paid calls are allowed and why not.

## 6. Fit, plans, notifications

- `lib/phirstmaxx/fitting.ts`: `windowsFor` (people from `pm_people` with waking, buffers, home place, car, a pet from `pm_pets`; `pm_blocks` in range; the Family calendar's appointments as busy for everyone through the adapter, all-day and PhirstMaxx-sourced entries excluded; `pm_waking` rows as day overrides), `fitsForThing` (eight-week horizon; `pm_travel` first, the engine estimate when no row), `fitForWindow`, `thingsForWindow` (ready things ranked by fit verdict then score).
- `lib/phirstmaxx/legs.ts` (pure): legs per person from a fit — leave by, travel, arrive, time there, home by — and their words ("Leave by 12:10 · 55 min drive · there 13:05–16:30 · home by 17:25").
- `lib/phirstmaxx/plans.ts`: `proposePlan` (expires at its own start; the proposer's "yes" recorded; the others told with Yes / No in the words, not through the budget), `respondToPlan` (one answer per person; **all yes → accepted** → `writePlanToCalendar` → legs stored → everyone told "both agreed — it's on, leave by 12:10"; a no → declined, the proposer told; "another time" leaves it proposed; anything but a proposed plan → 409), `cancelPlan`, `markDone` (done, a "Did <thing>" note seeded on the family timeline asking for a photo, `done_count` up), `listPlans` with responses and legs, `expireProposals`, `markConflicts` (an accepted plan no longer inside a together-window gets a reason and both are told once), `engineProposals` (firm together-windows of three hours or more in the next fortnight with no plan → the best fitting thing → a proposal by `engine`, at most two a week per space, never two for one window), `leaveByReminders` (accepted plans starting within two hours, once per plan per person).
- `lib/phirstmaxx/notify.ts`: `notifyPerson` always writes a `pm_notifications` row, then delivers: `counts: false` (a partner's answer, something the person started) goes by web push and the Telegram fallback for Phil without touching the interruption budget; `counts: true` (engine proposals, research results) goes through `interrupt()`. `listNotifications`, `markRead`.
- `lib/phirstmaxx/adapter.ts` is the one file that touches other sections: `familyBusyEvents`, `writePlanToCalendar` and `removePlanFromCalendar` (through `lib/family/resources.ts`, so an accepted plan reaches the Google Family calendar as an appointment with `source = 'phirstmaxx'`), `seedTimelineNote`.
- **Cron**: `/api/cron/phirstmaxx` every 15 minutes (in `SCHEDULE`, the tick's `HANDLERS` and the schedule test); per space, as the earliest `pm_people` row so a space is worked once: expire proposals, mark conflicts, engine proposals, re-research what is due (`next_recheck_at` passed, or an accepted plan within 48 h whose thing was not checked in 24 h), leave-by reminders. Body in `lib/phirstmaxx/tick.ts`.

## 7. Routes (`app/api/phirstmaxx/*`)

Every route takes the family space through `pmCtx` (`?space=` or `body.space` optional); a wrong method is 405; an RLS refusal is 403; no public GET.

| Route | Does |
|---|---|
| `drops` POST | JSON or multipart (fields + `file`, image or PDF, 15 MB, stored in the `phirstmaxx` bucket **before** the row) → **202** `{id, duplicate, thing_id}`; GET the space's drops with their thing and research runs |
| `inbox/[token]` POST | **public, POST only**; token resolved by `lib/system/pmInbox.ts` (the one service-client import), then `createDrop` as the owner through `withUser`; unknown token → bare 404; rate-limited per IP |
| `things` GET | filters `fits=week`, `indoor`, `dog=yes`, `max_km`, `max_cost`, `q`, `archived` |
| `things/[id]` GET / PATCH / POST | facts by key with source lines, travel per person per mode, fits and the next fit; PATCH hand edits (column + `hand_edited` + a person fact); POST `rerun`, `archive`, `unarchive`, `propose` |
| `things/[id]/image` GET | 302 to a signed URL |
| `plans` GET / POST, `plans/[id]` POST | list; propose (`kind: "hold"` needs no thing); `respond`, `cancel`, `done` |
| `week` GET / POST | `?week=` → `weekData`; `save`, `undo`, `resize`, `update`, `delete`, `copy_last_week` (trim), `save_pattern`, `apply_pattern` (replace), `delete_pattern`; every answer carries the redrawn week |
| `settings` GET / POST | my row, places, types, pets, research status, inbox hint; `person` (the research cap only by the instance owner), `place`, `type` (in use → 409), `pet`, `waking_override`, `rotate_inbox_token` (shown once) |
| `notifications` GET / POST | unread and limit; `read` |
| `questions` POST | the answer to "What's this place called?" → 202 |
| `share` POST | the PWA share target's multipart form → 303 to `/phirstmaxx/share?saved=<id>` |
| `home` GET | one read for the Home page |
| `import` POST | the importer's payload (§10); session or API secret |

Server modules behind them: `lib/phirstmaxx/{http,week,weekShape,things,settings,home,files,telegram}.ts`. `weekShape.ts` is pure (pattern ⇄ ranges as slots from Monday London 00:00, week shifts that keep wall-clock across a clock change, the last-used and ten-minute undo logic; 13 checks). `lib/system/apiTokens.ts` gained the token route family `phirstmaxx_drops` so a phone token can drop and do nothing else.

## 10. The importer (`scripts/phirstmaxx-import.mjs`, `lib/phirstmaxx/import.ts`, `/api/phirstmaxx/import`)

Dry run by default, `--apply`, `--undo`, `--since <iso>`. Reads `PHIRSTMAXX_OLD_DB_URL` (never printed) and the old Postgres in one read-only transaction with `pg` (added as a dev dependency), maps every table and POSTs one payload with `x-api-secret`; the route writes under RLS as Phil. Mapping (the table at the top of `import.ts`): members → `pm_people` updates (Phil's email → the caller, one other → the other member, else reported); locations → places; block types; availability blocks rounded **out** to the half hour, non-confirmed skipped, recurrence expanded twelve weeks ahead with `old_id "<id>:<date>"` and `local = false`; waking overrides fanned out per person; pets; ideas → a thing **and** a drop (`old:idea:<id>`), re-research queued only for things without a pin; plans with responses and legs; route overrides → `pm_travel` with provider `override`. Expenses, budget goals, contributions, memories, trips, astro events and notifications are counted under "phase 2, kept in the old database". Idempotent on `(space_id, old_id)`: a second run reports everything unchanged. `--undo` removes imported rows that are not marked local. **Not run for real**: no old database URL on this PC (checklist phase 5), and on 2026-11-24 the old project was unreachable (a Supabase incident) and Phil said not to touch it. **Proven without it (2026-11-24):** `--from-dump <file.json>` reads a dump in `readOld()`'s shape instead of the old database (`--since` still applies), `--space <id>` names the family space when the caller has more than one, and `docs/fixtures/phirstmaxx-old-dump.json` is a small made-up dump with the awkward cases in it (a weekly rule with a Christmas exception, an unconfirmed block, an idea with no pin, an unsaved place, a route whose coordinate key is written to four decimals where `coordKey` matches to three). `lib/phirstmaxx/import.dump.test.ts` runs that file through `buildPlan`: every table placed, the skips named, idempotent on a second pass. A dry run of the script from the fixture against the compiled e2e server (a seeded family space, port 3100) planned 49 blocks, 4 places, 4 types, 3 things + 5 facts + 3 drops, 2 plans, 2 legs, 1 travel, 1 research, and reported Kirsty unmapped because that space had one member — the honest answer. `ORS_API_KEY` and `YOUTUBE_API_KEY` were not in `.env.local` that night, so routing stays on the OSRM/Nominatim fallbacks and the YouTube reader stays off; `GOOGLE_MAPS_API_KEY` is deliberately absent.
